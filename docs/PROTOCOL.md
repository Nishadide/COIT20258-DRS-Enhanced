# DRS-Enhanced client and server protocol

COIT20258 Assessment 3. Version 1.0.

This document defines the only means by which the DRS-Enhanced client and
server communicate. No client class opens a database connection and no server
class references a JavaFX type. Any operation a screen needs must appear in the
operation table below before the screen is written.

## 1. Why this document exists first

The three tiers are built by three people at the same time. The client is
useless until the server answers, and the server is untestable until the client
calls it. Agreeing the message format before either exists means both can be
written in parallel against the same contract, and either side can be tested
against a stub of the other.

The protocol is therefore frozen before client or server code is written. A
change to this document after that point requires agreement from all three
members, because it invalidates work already done.

## 2. Transport

| Property | Value |
| --- | --- |
| Transport | TCP socket |
| Default port | 5050, overridable (see section 9) |
| Character encoding | UTF-8 |
| Framing | One JSON object per line, terminated by `\n` |
| Model | Request, then exactly one response |
| Connection lifetime | One connection per client session, held open from launch to exit |

Line delimited framing is used rather than length prefixing because Gson's
compact output contains no literal newline character, so a newline is an
unambiguous terminator. `BufferedReader.readLine` and `PrintWriter.println`
then provide framing with no custom parsing code.

The connection is held open for the session rather than opened per request.
This is required because the session token and its signing key, described in
section 7, are bound to the connection, and because reconnecting per request
would make the server's thread accounting meaningless.

### 2.1 Why JSON rather than Java object serialisation

Java object serialisation over `ObjectOutputStream` was considered and
rejected for three reasons.

1. Every transferred class would need to implement `Serializable`, which
   places a transport concern inside the 21 domain classes. The domain classes
   currently carry no persistence or transport dependency and that property is
   worth keeping.
2. Assessment 2 persisted its data as JSON, and Gson is already a dependency
   with adapters written for `LocalDateTime` and for the abstract `User`
   hierarchy. Those adapters are reused unchanged, so the serialisation code
   for the protocol is code that already exists and already passes tests.
3. A JSON message can be read in a terminal or a log file. This matters for
   evidence in the report and for diagnosing faults during integration.

## 3. Request envelope

```json
{
  "requestId": "f3c1a2b4-9d8e-4a7c-b6f5-0123456789ab",
  "operation": "report.submit",
  "sessionToken": "s-7f2a91c4e8b03d6a",
  "sentAt": "2026-10-15T09:14:22.481365",
  "payload": { },
  "signature": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"
}
```

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `requestId` | string, UUID | yes | Generated by the client. Echoed in the response so a reply can be matched to its request |
| `operation` | string | yes | One of the operations in section 5. Unknown values are refused with `UNKNOWN_OPERATION` |
| `sessionToken` | string | no | Issued by `auth.login`. Absent for the three public operations marked in section 5 |
| `sentAt` | ISO-8601 local date and time, microsecond precision | yes | The client's clock when the request was sent. Recorded, never trusted (section 7.2) |
| `payload` | object | yes | Operation specific. An empty object when the operation takes no arguments |
| `signature` | string, hex | no | HMAC-SHA256 over the canonical request (section 7.5). Required for every operation that requires a session |

## 4. Response envelope

```json
{
  "requestId": "f3c1a2b4-9d8e-4a7c-b6f5-0123456789ab",
  "status": "OK",
  "receivedAt": "2026-10-15T09:14:22.502118",
  "respondedAt": "2026-10-15T09:14:22.547903",
  "payload": { },
  "errorCode": null,
  "message": null
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `requestId` | string | Copied from the request |
| `status` | `OK` or `ERROR` | Whether the operation was carried out |
| `receivedAt` | timestamp | Server clock when the request was read |
| `respondedAt` | timestamp | Server clock when the response was written |
| `payload` | object or null | The result when `status` is `OK`, otherwise null |
| `errorCode` | string or null | One of section 6 when `status` is `ERROR` |
| `message` | string or null | Text suitable for display to the user |

A response is returned for every request, including a request the server
refuses. The client never has to distinguish a refusal from a dropped
connection by waiting for a timeout.

### 4.1 Errors are responses, not exceptions

A validation failure, a missing record and an access refusal are all normal
`ERROR` responses carrying an `errorCode`. The connection stays open. Only a
protocol level fault, meaning a line that is not valid JSON or a missing
`operation` field, closes the connection, because after such a fault the
server cannot know where the next message begins.

## 5. Operations

`Role` lists the roles permitted to invoke the operation. `Public` means no
session token is required. The server enforces this table; the client's
screens also hide what a user may not do, but that is a convenience and not a
control, because a modified client could call anything.

### 5.1 Session

| Operation | Role | Payload | Returns |
| --- | --- | --- | --- |
| `auth.login` | Public | `username`, `password` | `sessionToken`, `signingKey`, `user` |
| `auth.logout` | Any | none | `acknowledged` |
| `auth.changePassword` | Any | `newPassword` | `acknowledged` |
| `server.ping` | Public | none | `serverTime`, `version` |

`auth.login` returns the signing key once, on the login response only. The key
is never sent again in either direction. A client that loses it must log in
again.

### 5.2 Reports

| Operation | Role | Payload | Returns |
| --- | --- | --- | --- |
| `report.submit` | Public | `type`, `address`, `latitude`, `longitude`, `severity`, `description`, `reporterName`, `contactNumber` | `referenceNumber` |
| `report.findByReference` | Any | `reference` | `report` or `NOT_FOUND` |
| `report.findAll` | Coordinator, Administrator | none | `reports` |
| `report.nearby` | Coordinator, Administrator | `reference`, `radiusKm` | `reports` with `distanceKm` |

`report.submit` is public because the case study requires a member of the
public to lodge a report without an account. It is the only public operation
that writes.

### 5.3 Assessment

| Operation | Role | Payload | Returns |
| --- | --- | --- | --- |
| `assessment.assess` | Coordinator | `reference`, `severity`, `notes` | `assessment`, `priority` |
| `assessment.queueByPriority` | Coordinator | none | `reports` in priority order |
| `assessment.awaitingAssessment` | Coordinator | none | `reports` |
| `assessment.resolve` | Coordinator | `reference` | `acknowledged` |

### 5.4 Coordination

| Operation | Role | Payload | Returns |
| --- | --- | --- | --- |
| `coordination.allocate` | Coordinator | `reference`, `departmentIds` | `tasks`, `notificationResults` |
| `coordination.updateStatus` | Coordinator, Responder | `reference`, `taskId`, `status`, `note` | `statusUpdate` |
| `coordination.tasksForDepartment` | Responder, Coordinator | `departmentId` | `tasks` |
| `coordination.reportForTask` | Responder, Coordinator | `taskId` | `report` |
| `coordination.availableDepartments` | Coordinator | none | `departments` |
| `department.findAll` | Coordinator, Administrator | none | `departments` |
| `department.setAvailability` | Administrator, Coordinator | `departmentId`, `available` | `department` |

`coordination.allocate` takes a list of department identifiers, not one, so
the batch dispatch behaviour built in Assessment 2 survives the split into two
tiers as a single request rather than becoming one request per department.

A Responder may call `coordination.updateStatus` and
`coordination.tasksForDepartment` only for their own department. The server
checks the session's department against the task's department and returns
`ACCESS_DENIED` on a mismatch. This reproduces the `canUpdate` check that
`DepartmentResponder` performs in the domain model, on the server side where
it cannot be bypassed.

### 5.5 Alerts

| Operation | Role | Payload | Returns |
| --- | --- | --- | --- |
| `alert.issue` | Coordinator | `reference`, `type`, `affectedArea`, `message` | `alert`, `delivered` |
| `alert.findAll` | Coordinator, Administrator | none | `alerts` |

### 5.6 Accounts and audit

| Operation | Role | Payload | Returns |
| --- | --- | --- | --- |
| `account.create` | Administrator | `username`, `password`, `fullName`, `role`, `departmentId` | `user` |
| `account.deactivate` | Administrator | `username` | `acknowledged` |
| `account.activate` | Administrator | `username` | `changed` |
| `account.assignRole` | Administrator | `username`, `role` | `user` |
| `account.findAll` | Administrator | none | `users` |
| `audit.findAll` | Administrator | none | `entries` |
| `audit.verifyChain` | Administrator | none | `intact`, `brokenAtSequence` |

`audit.verifyChain` has no equivalent in Assessment 2. It walks the audit log
and recomputes the hash chain described in section 7.4, which is how the
non-repudiation claim is demonstrated rather than asserted.

### 5.7 Migration

| Operation | Role | Payload | Returns |
| --- | --- | --- | --- |
| `admin.migrate` | Administrator | `confirm` | counts per entity, `skipped` |

The specification requires Assessment 2 data to be loaded into the database
through the server rather than by a direct database import. This operation is
how that requirement is met. It is idempotent: a record whose primary key is
already present is counted as skipped, not inserted again, so running the
migration twice does not duplicate data.

### 5.8 Operations reserved for the two new features

These names are reserved now so that the two feature owners do not have to
alter this document, which would reopen the frozen protocol. Each owner
defines the payload for their own operations in their own section of the
report.

| Prefix | Owner | Feature |
| --- | --- | --- |
| `resource.*` | Member 2 | Resource allocation |
| `casualty.*` | Member 3 | Casualty registry |

## 6. Error codes

| Code | Meaning |
| --- | --- |
| `UNKNOWN_OPERATION` | The `operation` field is not in section 5 |
| `MALFORMED_REQUEST` | The line was not valid JSON, or a required envelope field was absent |
| `NOT_AUTHENTICATED` | The operation requires a session and no valid token was presented |
| `SESSION_EXPIRED` | The token was valid but its session has ended |
| `ACCESS_DENIED` | The session's role is not permitted this operation, or the record is outside the session's department |
| `SIGNATURE_INVALID` | The HMAC did not match the canonical request |
| `REPLAY_DETECTED` | This `requestId` was already processed on this session |
| `VALIDATION_FAILED` | The payload broke a domain rule. `message` carries the specific rule |
| `NOT_FOUND` | No record matches the identifier given |
| `CONFLICT` | The operation lost a race against another client, such as a resource already allocated |
| `STORAGE_FAILURE` | The database rejected the operation or was unreachable |
| `INTERNAL_ERROR` | An unexpected fault. The detail is logged on the server and not returned to the client |

`INTERNAL_ERROR` deliberately returns no detail. A stack trace or SQL fragment
returned to a client tells an attacker about the schema.

## 7. Security

The specification requires access rights, time stamping, encryption,
decryption and non-repudiation. Each is addressed below, with the member
responsible named, so that no requirement is left to be noticed at
integration.

### 7.1 Access rights

Enforced at two points, both on the server.

1. **Operation level.** Every request is checked against the `Role` column in
   section 5 before the operation runs. The check uses the role stored against
   the session on the server, not a role sent by the client.
2. **Record level.** A Responder is confined to their own department, as
   described in section 5.4. A record level check is required in addition to
   the operation level check because two users may hold the same role and
   still be entitled to different records.

Owner: Nishadi, as part of the server.

### 7.2 Time stamping

Three timestamps are recorded for every request: `sentAt` from the client, and
`receivedAt` and `respondedAt` from the server. Every audit entry and every
domain timestamp written to the database is taken from the server clock.

The client's `sentAt` is stored for diagnostics and never used as the time of
record. A client clock can be wrong, by accident or deliberately, and a system
whose audit trail depends on client clocks cannot establish the order in which
events occurred.

Owner: Nishadi, as part of the server.

### 7.3 Encryption and decryption

Two separate mechanisms, because the two requirements are different.

**Passwords are hashed, not encrypted.** Assessment 2 stored unsalted
SHA-256 digests and its report recorded that as prototype level. DRS-Enhanced
replaces this with PBKDF2 with HMAC-SHA256, a per-user random salt of 16 bytes
and 210,000 iterations. Hashing is one way by design, so this satisfies
password storage but does not by itself satisfy the encryption and decryption
requirement.

**Sensitive fields are encrypted reversibly.** AES-256 in GCM mode, with a
random 12 byte initialisation vector per value, stored as
`base64(iv) + ":" + base64(ciphertext)`. The server encrypts before the
insert and decrypts after the select, so the plaintext never reaches the disk
and the client never sees ciphertext. GCM is chosen over CBC because it
authenticates the ciphertext, so a value altered directly in the database is
detected on decryption rather than returning corrupted plaintext.

Fields encrypted at rest:

| Table | Column | Reason |
| --- | --- | --- |
| `reporters` | `contact_number` | Personal contact detail of a member of the public |
| `casualties` | `name`, `contact_number`, `notes` | Health information, defined by Member 3 |

The key is read from configuration and is not committed to the repository. A
development key is generated on first run and written to a file excluded by
`.gitignore`, and the report records that a production system would hold the
key in a managed key store rather than on the application host.

Owner: Member 3, as part of data security. Nishadi provides the
`password_salt` column in the schema so that no second schema change is
needed when PBKDF2 lands.

### 7.4 Non-repudiation: the audit chain

The audit log is append only and hash chained. Each entry stores the hash of
the entry before it:

```
entryHash = SHA-256( sequenceNo | actor | action | timestamp | previousHash )
```

The first entry uses 64 zero characters as its `previousHash`. Because every
hash depends on all preceding entries, altering or deleting any entry breaks
the chain at that point and at every point after it. `audit.verifyChain`
recomputes the chain and reports the first sequence number at which it breaks.

A hash chain alone does not prevent an administrator with database access from
recomputing the whole chain after altering an entry. The report states this
limit plainly and names the usual remedies, which are an append only store or
periodic publication of the head hash to a separate system. Neither is in
scope for a university assessment, and claiming otherwise would be false.

### 7.5 Non-repudiation: request signing

Every request requiring a session carries an HMAC-SHA256 signature over the
canonical form of the request, computed with the per-session signing key
issued at login:

```
canonical = requestId + "\n" + operation + "\n" + sentAt + "\n" + compactJson(payload)
signature = hex( HMAC-SHA256( signingKey, canonical ) )
```

The payload is serialised by Gson with its fields in declaration order, so
both sides produce the same byte sequence for the same payload. The server
recomputes the signature and refuses a mismatch with `SIGNATURE_INVALID`.

The server also records every `requestId` seen on a session and refuses a
repeat with `REPLAY_DETECTED`. Without this a captured signed request could be
replayed, and a signature that can be replayed does not establish intent to
perform the action a second time.

Together these mean an actor cannot credibly deny having sent a request: the
signature could only have been produced with a key issued to their session,
and the request could not have been replayed by a third party.

Owner: Nishadi provides the mechanism in the protocol layer. Member 3 covers
it in the security section of the report.

### 7.6 What this design does not claim

The socket is not TLS encrypted, so the protocol protects integrity and
authenticity on the wire but not confidentiality. A password therefore travels
in the clear on the login request, which is acceptable only because the
application runs on a trusted local network for assessment purposes. The
report states this as a known limitation with the remedy named, which is
`SSLSocket` with a server certificate. Overstating the security of a
prototype is worse than documenting its limits.

## 8. Threading

```
DrsServer
  ServerSocket.accept() in a loop on the main server thread
    each accepted socket is submitted to a fixed thread pool
      ClientHandler.run() reads lines until end of stream
        for each line: parse, authorise, verify signature, dispatch, respond
```

| Decision | Choice | Reason |
| --- | --- | --- |
| Concurrency model | Thread per client, drawn from a fixed pool of 32 | The specification requires a multi-threaded server. A pool bounds thread creation so a flood of connections cannot exhaust memory |
| Shared mutable state | None in the handlers | Each handler holds only its own socket and session. Everything shared lives in the database |
| Session store | One `ConcurrentHashMap` keyed by token | Read on every request and written on login and logout |
| Contention | Database transactions | Two clients competing for the same row are serialised by the database, not by a Java lock |
| Isolation level | `REPEATABLE READ`, the MySQL default | Sufficient with explicit row locking where it is needed |

Where a read must be followed by a conditional write, the read takes an
explicit row lock:

```sql
SELECT available_units FROM resources WHERE resource_id = ? FOR UPDATE
```

The lock is held to the end of the transaction, so a second client reading the
same row waits rather than reading a value that is about to change. This is
the mechanism the resource allocation feature relies on, and the concurrency
test for that feature exists to prove it works.

Java synchronisation is deliberately not used for this purpose. A `synchronized`
block protects one server process only, and a design whose correctness depends
on there being exactly one server process is not a three-tier design.

## 9. Configuration

No host, port, database name, user or password is hardcoded. All are read in
this order, first match winning:

1. A JVM system property, such as `-Ddrs.server.port=6060`
2. An environment variable, such as `DRS_SERVER_PORT`
3. `db.properties` on the classpath
4. The built in default

| Key | Default | Used by |
| --- | --- | --- |
| `drs.server.host` | `localhost` | Client |
| `drs.server.port` | `5050` | Client and server |
| `drs.db.host` | `localhost` | Server |
| `drs.db.port` | `3306` | Server |
| `drs.db.name` | `drs_enhanced` | Server |
| `drs.db.user` | `root` | Server |
| `drs.db.password` | empty | Server |
| `drs.db.createSchema` | `true` | Server |

The override order exists so that a marker whose MySQL root password differs
from the committed default can run the application by setting one property,
without editing a tracked file.
